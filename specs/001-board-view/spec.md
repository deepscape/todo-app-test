# Feature Specification: 칸반 보드 조회

**Feature Branch**: `001-board-view`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "전체 티켓을 4개 칼럼(BACKLOG, TODO, IN_PROGRESS, DONE)별로 그룹화하여 칸반 보드를 조회하는 기능. 각 칼럼 내 티켓은 position 오름차순으로 정렬되고, 각 티켓에는 기한 초과 여부(isOverdue)가 표시된다. Done 칼럼은 완료된 지 24시간 이내인 티켓만 보여준다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 보드 전체 현황 한눈에 보기 (Priority: P1)

사용자가 앱을 열면, 자신의 모든 할 일이 진행 상태(대기/할 일/진행 중/완료)에 따라
4개의 칼럼으로 나뉘어 한 화면에 표시된다. 사용자는 스크롤이나 추가 조작 없이
지금 무엇을 해야 하고 무엇이 진행 중인지 즉시 파악할 수 있다.

**Why this priority**: 보드 조회는 이 앱의 핵심 진입점이다. 티켓 생성/수정 등
다른 모든 기능은 사용자가 먼저 현재 보드 상태를 볼 수 있어야 의미가 있다.

**Independent Test**: 여러 상태의 티켓이 존재하는 상태에서 보드를 조회했을 때,
각 티켓이 자신의 상태에 해당하는 칼럼에 정확히 나타나는지 확인하는 것만으로
독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 대기(Backlog), 할 일(Todo), 진행 중(In Progress), 완료(Done) 상태의
   티켓이 각각 존재할 때, **When** 사용자가 보드를 조회하면, **Then** 각 티켓이
   자신의 상태에 해당하는 칼럼에 표시된다.
2. **Given** 어떤 상태에도 티켓이 없을 때, **When** 사용자가 보드를 조회하면,
   **Then** 해당 칼럼은 비어 있는 상태로 표시된다 (오류 없음).

---

### User Story 2 - 칼럼 내 우선순위/작업 순서 확인 (Priority: P2)

사용자가 각 칼럼 안에서 자신이 정해둔 작업 순서(드래그앤드롭으로 배치한 순서)
그대로 티켓 목록을 본다. 순서가 매번 뒤섞이지 않아, 사용자는 다음에 무엇을
먼저 처리할지 일관되게 예측할 수 있다.

**Why this priority**: 순서가 보장되지 않으면 사용자가 직접 정리한 우선순위가
매 조회마다 흐트러져 신뢰할 수 없는 보드가 된다. 조회 기능의 핵심 가치 중
하나다.

**Independent Test**: 한 칼럼에 여러 티켓을 특정 순서로 배치한 뒤 보드를
반복 조회했을 때, 매번 동일한 순서로 반환되는지 확인하는 것으로 독립적으로
검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 같은 칼럼에 순서가 다른 티켓 3개가 있을 때, **When** 사용자가
   보드를 조회하면, **Then** 정해진 순서(먼저 배치된 것부터)대로 티켓 목록이
   반환된다.

---

### User Story 3 - 기한 초과 항목과 최근 완료 항목 식별 (Priority: P3)

사용자는 어떤 할 일이 종료예정일을 넘겼는지, 그리고 최근에 완료한 항목이
무엇인지 보드에서 바로 알아볼 수 있다. 오래전에 완료된 항목은 보드를 어지럽히지
않도록 자동으로 숨겨진다.

**Why this priority**: 기한 초과 표시와 완료 항목 정리는 보드를 "지금 신경 써야
할 것"에 집중시켜 사용자 생산성을 높이지만, 보드가 각 상태별로 티켓을 보여주는
핵심 기능(User Story 1)이 먼저 갖춰져야 의미가 있는 부가 가치다.

**Independent Test**: 종료예정일이 지난 미완료 티켓과, 완료 시각이 24시간
이내/이후인 완료 티켓을 각각 준비한 뒤 보드를 조회하여, 기한 초과 표시와
완료 항목 노출 여부가 규칙대로 나타나는지 확인하는 것으로 독립적으로 검증
가능하다.

**Acceptance Scenarios**:

1. **Given** 종료예정일이 오늘 이전이고 완료되지 않은 티켓이 있을 때, **When**
   사용자가 보드를 조회하면, **Then** 해당 티켓은 기한 초과로 표시된다.
2. **Given** 종료예정일이 지났지만 이미 완료 처리된 티켓이 있을 때, **When**
   사용자가 보드를 조회하면, **Then** 해당 티켓은 기한 초과로 표시되지 않는다.
3. **Given** 완료된 지 24시간이 지난 티켓이 있을 때, **When** 사용자가 보드를
   조회하면, **Then** 해당 티켓은 완료 칼럼에 나타나지 않는다.
4. **Given** 완료된 지 24시간 이내인 티켓이 있을 때, **When** 사용자가 보드를
   조회하면, **Then** 해당 티켓은 완료 칼럼에 나타난다.

### Edge Cases

- 등록된 티켓이 하나도 없을 때: 4개 칼럼 모두 빈 목록으로, 오류 없이 정상
  응답한다.
- 종료예정일이 설정되지 않은 티켓: 기한 초과 여부는 항상 "아니오"로 판정한다.
- 완료 처리된 적 없는(completedAt이 없는) 대기/할 일/진행 중 티켓: 완료 칼럼
  노출 규칙과 무관하며 항상 자신의 상태 칼럼에 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 존재하는 모든 티켓을 상태값 기준 4개 그룹(대기, 할 일,
  진행 중, 완료)으로 분류하여 한 번의 조회로 반환해야 한다.
- **FR-002**: 시스템은 각 그룹 내 티켓을 사용자가 정한 순서(오름차순)대로
  정렬하여 반환해야 한다.
- **FR-003**: 시스템은 각 티켓에 대해 종료예정일이 지났고 아직 완료되지 않았는지
  여부를 나타내는 기한 초과 표시를 함께 반환해야 한다.
- **FR-004**: 완료 그룹에는 완료 처리 후 24시간이 지나지 않은 티켓만 포함해야
  한다.
- **FR-005**: 어떤 그룹에 해당하는 티켓이 없어도 시스템은 오류 없이 빈 목록을
  반환해야 한다.
- **FR-006**: 시스템은 조회된 티켓의 전체 개수를 함께 제공해야 한다.

### Key Entities *(include if feature involves data)*

- **티켓(Ticket)**: 사용자가 관리하는 할 일 단위. 제목, 설명, 우선순위, 현재
  상태(대기/할 일/진행 중/완료), 칼럼 내 순서, 시작예정일, 종료예정일, 실제
  시작 시각, 완료 시각을 가진다. 보드 조회 시 이 정보에 더해 기한 초과 여부가
  파생되어 함께 제공된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 앱 진입 후 1초 이내에 전체 보드 현황(모든 칼럼과 티켓)을
  확인할 수 있다.
- **SC-002**: 티켓이 1000개 존재하는 상태에서도 보드 조회 결과가 지연 없이
  표시된다.
- **SC-003**: 사용자가 직접 배치한 칼럼 내 순서는 100% 정확히 유지되어 조회될
  때마다 동일한 순서로 나타난다.
- **SC-004**: 기한을 넘긴 미완료 티켓은 100% 빠짐없이 기한 초과로 표시된다.

## Assumptions

- 인증/권한 구분이 없는 단일 사용자 환경이므로, 보드 조회는 별도의 사용자
  필터링 없이 전체 티켓을 대상으로 한다 (기존 프로젝트 범위 정의에 따름).
- "완료된 지 24시간 이내"의 기준 시각은 조회가 이루어지는 시점이다.
- 종료예정일이 없는 티켓은 기한 초과 판정에서 제외된다(항상 "아니오").
- 칼럼 내 정렬 기준(순서값)은 티켓 생성/이동 시 별도 기능(티켓 생성, 순서
  변경)에서 이미 관리되고 있다고 가정하며, 이 기능은 그 값을 읽어 정렬만
  수행한다.
