# Feature Specification: 티켓 상세 조회/수정/삭제

**Feature Branch**: `002-ticket-detail-crud`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "티켓 상세 조회, 수정, 삭제 기능. 사용자는 특정 티켓의 전체 정보를 조회할 수 있고, 제목/설명/우선순위/시작예정일/종료예정일을 부분 수정할 수 있으며, 더 이상 필요 없는 티켓을 영구 삭제할 수 있다. 존재하지 않는 티켓에 대한 조회/수정/삭제는 404 에러를 반환한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 티켓 상세 정보 확인 (Priority: P1)

사용자가 보드에서 특정 티켓을 선택하면, 그 티켓의 모든 정보(제목, 설명,
우선순위, 상태, 일정, 기한 초과 여부 등)를 확인할 수 있다.

**Why this priority**: 상세 조회는 수정과 삭제 이전에 사용자가 대상 티켓의
현재 정보를 정확히 파악하기 위한 전제 조건이다. 이 없이는 수정/삭제 자체가
의미를 갖기 어렵다.

**Independent Test**: 티켓을 하나 생성한 뒤 해당 id로 상세 조회를 요청하여,
생성 시 입력한 값과 시스템이 채운 값(id, 상태, 생성/수정 시각 등)이 모두
정확히 반환되는지 확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 존재하는 티켓의 id를 알고 있을 때, **When** 사용자가 그 티켓의
   상세 정보를 요청하면, **Then** 해당 티켓의 모든 필드(기한 초과 여부
   포함)가 반환된다.
2. **Given** 존재하지 않는 티켓 id로 상세 정보를 요청했을 때, **When** 조회를
   시도하면, **Then** 티켓을 찾을 수 없다는 오류가 반환된다.

---

### User Story 2 - 티켓 정보 수정 (Priority: P1)

사용자는 이미 등록한 티켓의 제목, 설명, 우선순위, 시작예정일, 종료예정일 중
바뀐 부분만 골라 수정할 수 있다. 수정하지 않은 필드는 그대로 유지된다.

**Why this priority**: 할 일의 세부 내용은 진행하면서 자주 바뀐다 (마감일
변경, 우선순위 재조정 등). 이 기능 없이는 사용자가 잘못 입력한 티켓을
삭제하고 새로 만들어야 하므로 핵심 사용성 요구다.

**Independent Test**: 티켓을 생성한 뒤 제목만 바꿔 수정 요청을 보내고, 응답에
새 제목과 나머지 기존 값이 그대로 남아있는지 확인하는 것으로 독립적으로
검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 존재하는 티켓이 있을 때, **When** 사용자가 제목만 바꿔서
   수정을 요청하면, **Then** 제목만 바뀌고 나머지 필드는 그대로 유지된다.
2. **Given** 존재하는 티켓이 있을 때, **When** 사용자가 설명이나
   시작예정일/종료예정일을 비우도록(삭제하도록) 요청하면, **Then** 해당
   필드가 비워진다.
3. **Given** 존재하지 않는 티켓 id로 수정을 요청했을 때, **When** 수정을
   시도하면, **Then** 티켓을 찾을 수 없다는 오류가 반환된다.
4. **Given** 존재하는 티켓이 있을 때, **When** 사용자가 제목을 200자
   초과로 입력하거나, 우선순위를 정해진 값 외의 것으로 입력하거나, 종료
   예정일을 과거 날짜로 입력하면, **Then** 수정이 거부되고 이유가 안내된다.

---

### User Story 3 - 불필요한 티켓 삭제 (Priority: P2)

사용자는 더 이상 필요 없는 티켓을 완전히 제거하여 보드를 정리할 수 있다.

**Why this priority**: 삭제는 목록 정리에 유용하지만, 상세 조회/수정만큼
빈번하게 필요하지 않고 되돌릴 수 없는 작업이라 신중하게 다뤄지는 부가
기능이다.

**Independent Test**: 티켓을 하나 생성한 뒤 삭제 요청을 보내고, 이어서 같은
id로 상세 조회를 시도했을 때 더 이상 존재하지 않는다는 결과가 나오는지
확인하는 것으로 독립적으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 존재하는 티켓이 있을 때, **When** 사용자가 그 티켓을 삭제하면,
   **Then** 해당 티켓은 완전히 제거되어 이후 어떤 조회에서도 나타나지
   않는다.
2. **Given** 존재하지 않는 티켓 id로 삭제를 요청했을 때, **When** 삭제를
   시도하면, **Then** 티켓을 찾을 수 없다는 오류가 반환된다.

### Edge Cases

- 수정 요청에 아무 필드도 포함되지 않은 경우: 기존 티켓 정보가 변경 없이
  그대로 반환된다 (오류 아님).
- 이미 삭제된 티켓을 다시 삭제 요청하는 경우: 티켓을 찾을 수 없다는 오류가
  반환된다 (두 번째 삭제는 실패로 처리).
- 상태(진행 칼럼), 칼럼 내 순서, 시스템이 관리하는 시작/완료 시각은 이
  수정 기능으로 변경할 수 없다 — 다른 기능(순서 변경, 완료 처리)의 책임이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 존재하는 티켓의 id로 요청받았을 때 해당 티켓의 전체
  정보(기한 초과 여부 포함)를 반환해야 한다.
- **FR-002**: 시스템은 존재하지 않는 티켓 id로 상세 조회를 요청받으면
  티켓을 찾을 수 없다는 오류를 반환해야 한다.
- **FR-003**: 시스템은 제목, 설명, 우선순위, 시작예정일, 종료예정일 중
  전달된 필드만 부분적으로 수정할 수 있어야 하며, 전달되지 않은 필드는
  기존 값을 유지해야 한다.
- **FR-004**: 시스템은 수정 요청에서 설명, 시작예정일, 종료예정일을 명시적
  으로 비우도록(값 없음으로) 요청하면 해당 필드를 비워야 한다.
- **FR-005**: 시스템은 수정 시 제목/설명 길이, 우선순위 허용값, 종료예정일이
  오늘 이후여야 한다는 규칙을 티켓 생성 시와 동일하게 검증해야 한다.
- **FR-006**: 시스템은 존재하지 않는 티켓 id로 수정을 요청받으면 티켓을
  찾을 수 없다는 오류를 반환해야 한다.
- **FR-007**: 시스템은 이 수정 기능을 통해 상태(진행 칼럼), 칼럼 내 순서,
  시스템이 관리하는 시작/완료 시각이 변경되지 않도록 해야 한다.
- **FR-008**: 수정이 성공하면 시스템은 마지막 수정 시각을 현재 시각으로
  갱신해야 한다.
- **FR-009**: 시스템은 존재하는 티켓의 id로 삭제를 요청받으면 해당 티켓을
  영구적으로 제거해야 하며, 제거된 티켓은 이후 어떤 조회에도 나타나지
  않아야 한다.
- **FR-010**: 시스템은 존재하지 않는 티켓 id로 삭제를 요청받으면 티켓을
  찾을 수 없다는 오류를 반환해야 한다.

### Key Entities *(include if feature involves data)*

- **티켓(Ticket)**: 001-board-view에서 정의한 것과 동일한 엔티티. 이 기능은
  새 속성을 추가하지 않으며, 기존 티켓 하나를 대상으로 조회/부분 수정/삭제
  한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 티켓 id만으로 1초 이내에 해당 티켓의 전체 정보를
  확인할 수 있다.
- **SC-002**: 부분 수정 요청은 전달된 필드만 반영하고, 전달되지 않은 필드는
  100% 정확히 기존 값을 유지한다.
- **SC-003**: 존재하지 않는 티켓에 대한 조회/수정/삭제 시도는 100% 명확한
  "찾을 수 없음" 오류로 안내되어 사용자가 혼란 없이 다음 행동을 판단할 수
  있다.
- **SC-004**: 삭제된 티켓은 삭제 직후 이루어지는 모든 조회에서 예외 없이
  나타나지 않는다.

## Assumptions

- 인증/권한 구분이 없는 단일 사용자 환경이므로, 조회/수정/삭제는 소유권
  확인 없이 티켓 id만으로 식별된다 (기존 프로젝트 범위 정의에 따름).
- 삭제는 하드 삭제(복구 불가)이며, 되돌리기(undo)나 휴지통 기능은 이번
  범위에 포함되지 않는다.
- 수정 가능한 필드 집합(제목, 설명, 우선순위, 시작예정일, 종료예정일)은
  티켓 생성 시 사용자가 입력하는 필드와 동일하다 — 상태 변경과 순서 변경은
  각각 별도 기능(완료 처리, 순서 변경)의 책임이다.
